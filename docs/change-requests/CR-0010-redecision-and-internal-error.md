# CR-0010 재판정 요청 경로와 내부 오류 응답 (질문)

- 상태: **질문(헤드 결정 대기).** 구현하지 않았다. 지시서 1: "계약이 모호하면 구현하지 말고 변경 요청으로 질문".

## 질문 1. 정책 버전이 바뀐 뒤의 재판정 (RG-12)

- 계약 문장: INTERFACES I5 "정책 버전이 바뀐 뒤의 재판정은 같은 `submission_id`에 새 `GateDecision`을 더하고 가장 최근 것이 현재 판정이다." (CR-0003도 같은 취지)
- 현재 동작(코드를 읽어 도출, 실행으로 재현하지 않음): `submission_id`는 조합의 해시(gate.py:85)이고 `put_submission`은 같은 조합이면 기존 접수를 돌려준다. `advance`는 `RECEIVED`만 진행한다(gate.py:257-260). 그래서 `DECIDED`가 된 접수는 정책이 바뀌어도 다시 판정되지 않는다. 두 번째 판정은 생기지 않는다(`RECHECK_FAILED`는 판정을 더하지 않고 412 FAILED_PRECONDITION으로 끝난다).
- 모호한 점(이 문장만으로 정해지지 않는다):
  1. **무엇이 재판정을 일으키는가.** 정책 버전 변경을 게이트가 스스로 알아채 자동 재판정하는가, 누군가 요청하는가(I5에 재판정 메서드나 경로가 없다 - HTTP.md I5 표 확인).
  2. **어느 접수가 대상인가.** 반려된 것만인가, PASS 난 것도인가(PASS 릴리스는 불변이어야 하고 `release_id`가 있다). CR-0003은 "정책 때문에 반려된 접수(`POLICY_INCOMPLETE`)"만 말하지만, D53 이후 코드는 `POLICY_INCOMPLETE`를 내지 않는다(grep 결과 release_gate/ 안에 없음). 이 코드가 아직 계약에 남아 있는 의미가 무엇인가.
  3. 필수 검사 4종이 코드에 고정이고 임계치가 없으므로 **정책 버전이 바뀌어도 판정이 달라질 수 있는 입력은 `require_lineage_runtime_match`뿐**이다. 그렇다면 정책 버전 변경만이 아니라 검수 기록 변경(임상 승인이 나중에 생김)도 재판정 사유인가. 보고서 RG-12의 예가 후자다.
  4. 사람이 이미 한 `GateApproval`(REJECT)이 있는 접수는 재판정 대상에서 빼는가(승인자의 결정 위에 자동 판정을 덮으면 D53과 충돌할 수 있음).
- 제안(미정): 재판정을 요청 경로(`POST /v1/submissions`에 같은 조합을 다시 보내면 자동 반려 접수에 한해 `RECEIVED`로 되돌려 새 판정을 더함)로 둔다. 이 경우 I5의 "중복 제출은 기존 접수 반환" 규칙이 바뀌므로 계약 변경이다. 그 전까지 `docs/boundary.md`에 "재판정 없음"을 한계로 적는 것은 이 영역이 할 수 있다.

## 질문 2. 서버가 직접 내는 5xx의 BoundaryError 코드 (RG-10 연관)

- RG-10 수정으로 500 본문(예기치 못한 예외)을 `BoundaryError` 스키마에 맞추면서 `code`를 `UNAVAILABLE`로 했다. 이유: 코드 열거에 내부 오류가 없고(CONVENTIONS 3절), 클라이언트는 5xx를 `UNAVAILABLE`로 읽는다(HTTP.md 12행). 상태 줄은 500을 유지했다.
- 문제: `UNAVAILABLE`은 `retryable: true`다. 서버 결함도 재시도 가능으로 표시된다. CONVENTIONS 9절은 서비스가 직접 5xx를 내는 일을 정해 두지 않았다.
- 요청: (a) 상태를 503으로 통일할지, (b) 내부 오류용 코드를 열거에 추가할지, (c) 현재대로 둘지. 결정 전까지 현재대로다.
