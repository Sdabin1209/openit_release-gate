# ADR-0005: 토큰·역할 구조와 X-Openit-User 신뢰 경계

- 상태: 채택 (D85, D88 U7로 승인에도 적용)
- 날짜: 2026-10-28 (작성 시점의 코드·문서 기준. 결정 시점은 근거 항목에 적는다)

## 맥락

사람(승인자, 운영자)과 서비스(survey-service, ops-feedback, 수집기)가 같은 HTTP 면을 쓴다. 인증 방식 자체는 gateway의 일이다.

## 결정

읽기 토큰과 쓰기 토큰을 분리하고, 쓰기 토큰은 **역할에 묶는다**(`GATE_WRITE_TOKENS=역할=토큰,…`). 역할: `release-approver`(승인), `operator`(활성화), `ops-feedback`(롤백 요청, 서비스 역할), 제출 역할(`question-authoring`, `model-lab`, `release-gate-collector`, `operator`). 사람 행위자는 gateway가 인증한 뒤 붙이는 `X-Openit-User`로 정한다: 승인·활성화·롤백 모두 헤더가 없으면 401(서비스 역할 제외, 승인은 예외 없음), 본문의 자기 신고 값은 쓰지 않는다. 토큰은 `read_secret(NAME)`으로 파일에서 받는다(D84).

## 왜 (따른 표준과 근거)

- 근거: D42(역할은 토큰에 묶임), D69(승인자 식별은 X-Openit-User), D85(activate·rollback 행위자), D88 U7(승인자 신원은 개인 식별 필수), D84(비밀은 파일). 역할을 토큰에 묶는 이유: 본문 값은 호출자가 마음대로 쓸 수 있으므로 권한 판단에 쓰지 않는다(최소 권한).
- 신뢰 경계: `X-Openit-User`를 믿는 것은 이 서비스가 gateway 뒤 내부망에 있고 gateway가 클라이언트가 보낸 같은 이름의 헤더를 지우고 자기 값으로 덮는다는 전제 위에서다. 이 영역에서는 그 전제를 **확인하지 못했다**(gateway 설정은 읽기 허용 밖). 거부·실패 시도는 `attempts`와 접근 로그에 역할·사용자와 함께 남는다.

## 검토한 대안과 버리는 이유

- 서명된 사용자 토큰(JWT): 사람 인증 방식은 deploy와 운영이 정한다(D69). 이 영역이 자체 사용자 관리를 두지 않는다. 버림.
- 헤더 없을 때 본문 값 사용(이전 동작): 위조 가능. D88로 폐기.

## 결과

읽기 토큰은 역할 구분 없이 전부 읽는다(감사 B2, L). 토큰은 정적 문자열이라 만료·폐기는 재시작으로만 한다.

## 되돌리는 조건

gateway 없이 직접 노출해야 하면 헤더 신뢰를 버리고 이 영역이 서명 검증을 해야 한다.
