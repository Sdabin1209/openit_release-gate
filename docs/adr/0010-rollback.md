# ADR-0010: 롤백 설계

- 상태: 채택
- 날짜: 2026-10-28 (작성 시점의 코드·문서 기준. 결정 시점은 근거 항목에 적는다)

## 맥락

운영 관측이 품질 저하를 보고 이전 릴리스로 되돌려야 한다.

## 결정

롤백은 `RollbackRequest`를 받아 **같은 절차**로 처리하고 `RollbackReceipt`(APPLIED 또는 REJECTED + 사유)를 남긴다. `from`이 현재 활성이고 `to`가 해시 검증을 통과하는 PASS 릴리스이며 `from != to`일 때만 포인터를 바꾼다(`cause=ROLLBACK`). 같은 `request_id`는 같은 결과(다른 내용이면 CONFLICT). 거부도 영수증으로 남는다. 자동 롤백은 하지 않는다: 사람이 승인한다(D88 U11, 기준값은 비움).

## 왜 (따른 표준과 근거)

- 근거: 브리프 4절('운영 관측의 롤백 요청을 받아 같은 절차로 처리하고 기록한다'), 포인터 비교 후 교체(ADR-0004), 멱등 규칙. 되돌릴 대상을 다시 검증하는 이유: 변조·손상된 번들로 되돌리면 환자 경로에 나간다(`test_rollback_to_corrupt_release_is_rejected`).
- 롤백 대상이 정리(PRUNED)되면 거부된다. 보호 규칙(활성·직전·최근 N)이 이를 막는다(ADR-0009).

## 검토한 대안과 버리는 이유

- 이전 릴리스를 새 릴리스로 재승인: 사람 승인 단계를 또 요구해 장애 중 되돌림이 느려진다. 버림(근거 기록은 없고 설계 판단).
- 포인터 직접 수정: 감사·검증 우회. 버림.

## 결과

롤백 요청 권한은 `ops-feedback`, `operator`(설정 `GATE_ROLLBACK_ROLES`).

## 되돌리는 조건

자동 롤백 기준이 사용자 결정으로 정해지면 요청 생성 쪽(ops-feedback)에서 `auto_submit`으로 켠다. 이 영역의 처리 절차는 같다.
