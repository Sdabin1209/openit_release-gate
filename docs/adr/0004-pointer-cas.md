# ADR-0004: 활성 포인터는 비교 후 교체, 영수증과 한 트랜잭션

- 상태: 채택
- 날짜: 2026-10-28 (작성 시점의 코드·문서 기준. 결정 시점은 근거 항목에 적는다)

## 맥락

활성 릴리스를 가리키는 포인터는 서빙이 읽고, 활성화·롤백은 여러 호출자(operator, ops-feedback)가 동시에 요청할 수 있다. 중간 상태가 보이면 안 된다.

## 결정

`pointer_history(pointer_version PK, record)`에 **추가만** 한다. 변경은 한 트랜잭션에서 '기대한 현재 버전'과 '새 버전 = 현재 + 1'을 확인하고(비교 후 교체), 롤백 영수증도 같은 트랜잭션에 저장한다. 경쟁에서 진 쪽은 False이고 호출자가 최대 5번 다시 판단한다. 활성화는 해시 검증을 마친 **뒤에** 포인터를 바꾼다.

## 왜 (따른 표준과 근거)

- 근거: 낙관적 동시성 제어(compare-and-swap)는 잠금 대기 없이 정합성을 지키는 표준 방식이고, 이력을 추가 전용으로 두면 롤백과 감사가 쉽다(design.md 7절). 영수증을 같은 트랜잭션에 두는 이유: 포인터는 바뀌었는데 영수증이 없거나 그 반대인 상태가 생기면 같은 `request_id` 재전송이 멱등하지 않다(CONVENTIONS 멱등 규칙; 시험 `test_pointer_switch_is_all_or_nothing`).
- 재시도 횟수 5의 근거: 근거 기록 없음(설계 판단, 측정 안 함).

## 검토한 대안과 버리는 이유

- 행 하나를 UPDATE하는 방식: 이력이 사라져 롤백·감사가 어렵다. 버림.
- 분산 잠금: 단일 DB 트랜잭션으로 충분하다. 버림.

## 결과

포인터 변경은 전부-아니면-전무다(시험으로 확인). 이력이 계속 늘지만 작다.

## 되돌리는 조건

여러 DB에 걸친 포인터가 필요해지면 CAS를 쓸 수 있는 다른 저장소가 필요하다.
