# ADR-0020: 사람용 요청에 서버 쪽 요청 전체 마감을 둔다 (D120)

- 상태: 채택
- 날짜: 2026-10-31
- 링크: 헤드 결정 D120(`head/DECISIONS.md`), deploy ADR 0048(gateway 시간 사슬)

## 맥락

gateway를 지나는 사람용 요청은 gateway가 `dial 1초 + response_header 13초`에서 끊는다(D119). 서버의 호출별 시한(DB 문장 3초, 이웃 읽기 10초)을 모두 합친 최악은 활성화 27초, 롤백 36초, 승인 128초로 gateway 상한보다 길었다(U427, `tests/test_exposure_budget.py`). 그러면 서버는 계속 일하는데 화면은 504를 받는다.

## 결정

- 사람용(`/v1/*`) 요청마다 **서버 쪽 요청 전체 마감**을 둔다. 기본 12.0초, 설정 `GATE_REQUEST_DEADLINE_SECONDS`. 마감은 **주입한 시계**로 잰다(ADR-0019): HTTP 면이 요청 시작에 마감을 정하고(`wiring/util.py RequestDeadlines`), 끝나면 거둔다.
- 각 DB 문장·트랜잭션은 시작 전에 남은 시간을 확인하고(0 이하이면 더 진행하지 않는다), PostgreSQL 연결 감시 타이머는 `min(문장 시한 + 1초, 남은 시간)`이다. 이웃(I1·I3) 호출은 읽기 시한을 `min(고정 시한, 남은 시간)`으로 한 복사본 클라이언트로 부른다(`with_timeout`).
- 마감을 넘기면 503 `UNAVAILABLE`(retryable)이다. 트랜잭션은 시작하지 않았거나 롤백되어 반쯤 쓴 상태가 없다. 같은 요청을 다시 보내도 안전하다: 접수는 조합 해시 ID로, 승인은 접수당 하나의 승인 ID로, 롤백은 `request_id`로, 활성화는 이미 활성이면 그대로 돌려주는 방식으로 멱등이다(기존 규칙).
- 주기 작업과 잡은 요청이 아니므로 마감이 없다(`current()`가 None).

## 왜

- 표준: 마감 전파(deadline propagation, gRPC deadline과 같은 방식). 바깥 마감 > 안쪽 호출 시한 사슬을 안쪽이 남은 시간으로 자른다.
- 값 12.0초: gateway 상한(1초 + 13초) 안에서 응답이 나가도록 상한에서 여유 2초를 뺀 사슬 설계 값이다. **측정한 값이 아니다.**

## 검토한 대안과 버리는 이유

- 호출별 시한만 줄이기: 승인은 8번의 이웃 호출 때문에 어떤 시한으로도 합이 상한 안이 되려면 호출마다 1초대가 되어 정상 경로를 해친다.
- gateway 상한 늘리기: 화면 대기가 길어지고 사슬(화면 > gateway > 서버)의 바깥을 키우는 일이라 헤드가 정한 사슬과 어긋난다.
- 전역 시간 patch로 시험: 블로킹 대기를 못 움직인다(ADR-0019).

## 결과

- 얻는 것: 서버가 화면보다 먼저 끝나거나 먼저 포기한다(503, 재시도 안전). 시험은 가짜 시계로 마감 직전 정상과 초과를 직접 만든다(`tests/test_request_deadline.py`).
- 감수하는 것: 마감 확인은 문장·트랜잭션·이웃 호출 경계에서만 한다. 어댑터 해시 검증 같은 파일 읽기 자체는 중간에 끊지 못한다(다음 문장·트랜잭션에서 걸린다). 커밋 문장이 마감 직전에 시작해 감시 타이머에 끊기면 커밋 여부가 모호할 수 있고, 그 경우도 같은 요청을 다시 보내면 멱등 규칙이 같은 결과를 낸다.

## 되돌리는 조건

- gateway 상한(사슬)이 바뀌면 기본값을 다시 정한다. 마감 확인이 파일 읽기 같은 긴 구간 때문에 모자라면 그 구간에 확인 지점을 더한다.
