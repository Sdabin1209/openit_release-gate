# ADR-0021: 한 제출·한 릴리스에 문항 세트(문진표) 여럿

- 상태: 채택
- 날짜: 2026-11-03 (헤드 지시 wo-320, 사용자 결정 2026-11-03: 문진표는 여럿이 함께 활성이고 세션마다 고른다)

## 맥락

계약 3.3.0 이전에는 판정 대상이 문항 세트 하나(`subject.question_set`)였고 릴리스도 세트 하나를 묶었다. 이제 서비스는 한 릴리스 안의 여러 문진표 중 세션마다 하나를 고른다. 게이트는 어느 세트가 어떤 모델과 함께 출고되는지를 한 판정으로 남겨야 한다.

## 결정

- `subject.question_sets`(ArtifactRef 배열, 1개 이상)로 받는다. 옛 `question_set`은 코드·스키마·문서에서 지웠다.
- 자동 검사는 **세트마다** 한다: I1 읽기와 content_hash 대조, 문진 스키마 적합, 임상 승인, U81 구조 대조. 하나라도 실패하면 조합 전체를 지금과 같은 사유 코드로 반려한다. 사유 문장에 세트 ID를 넣는다.
- bank의 `question_set_id`가 참조 id와 같고 `title`이 있는지 CONTRACT_COMPAT가 본다(문진 스키마 4.0.0 필수 필드). `QuestionSetRef.title`은 bank에서만 온다.
- 접수는 세트를 id 순으로 정렬해 저장하고 같은 id 중복을 거부한다(INVALID_RECORD, `details.reason=DUPLICATE_QUESTION_SET`). 순서만 다른 제출이 다른 접수가 되지 않게 한다(조합 해시가 접수 ID).
- 저장: 릴리스 디렉터리에 `question_banks/<id>.json`(세트마다). 단일 `question_bank.json`은 없앴다. 번들 tar도 같은 경로다. ID는 계약 패턴(`^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`)이라 파일 이름으로 안전하다.
- 판정 표의 `qs` 칸은 참조마다 `\x1e`를 앞에 붙여 이은 문자열이다. `find_decisions`는 `\x1e`+접두사가 어디든 들어 있으면 맞는다(목록 중 하나와 맞으면 반환). 열 추가가 없어 마이그레이션이 필요 없다.
- I4 `question-bank`: 매니페스트에 세트가 둘 이상이면 `question_set_id` 필수. 없으면 `INVALID_RECORD`(400), `details.reason=QUESTION_SET_REQUIRED`. 하나면 생략 가능. 응답에 `question_set_id`. 묶음에 없는 ID는 NOT_FOUND.
- 수집기: `watch.question_sets`가 가리키는 검수 완료 최신 세트 전부를 한 제출에 묶는다(세트 x 모델 조합이 아니라 모델 조합마다 제출 하나).

## 왜

- 세트마다 검사하는 이유: 세트 하나라도 임상 승인이 없거나 구조가 모델과 다르면 그 세트로 문진받는 환자에게 잘못된 값이 나간다. 안전 관문이므로 일부만 통과시키지 않는다(D30, D53, 지시).
- 세트를 묶어 한 판정으로 하는 이유: 릴리스가 세트를 여럿 묶어 활성 포인터 하나로 켜지므로 판정·승인도 같은 단위여야 한다(승인 기록과 릴리스가 어긋나지 않는다).
- 조회 키 이어붙이기를 고른 이유: 표를 하나 더 만들거나 열을 바꾸는 방안은 마이그레이션이 필요하다. 이 칸은 접두사 검색용 파생 값이고 정본은 레코드 JSON이라 형식만 바꿔도 안전하다. 검색은 전체 훑기(instr)이며 판정 수에 비례한다. 규모별 소요는 측정 안 함.

## 검토한 대안과 버리는 이유

- 세트마다 접수·판정을 따로: 한 릴리스에 묶을 때 판정 여럿의 합치기 규칙이 생기고 일부만 통과한 릴리스가 생긴다. 버림.
- 판정-세트 연결 표 추가: 마이그레이션 비용 대비 이득 없음. 버림.
- 옛 `question_set`을 함께 허용: 계약이 지웠다. 버림.

## 결과

- 얻는 것: 여러 문진표를 한 번에 검사·승인·출고. 감수하는 것: 세트 수만큼 I1 읽기가 늘고(`get_question_bank`, `get_reviews`) 승인 직전 재검사도 늘어난다. 한 세트의 문제가 조합 전체를 막는다.
- **동작 차이**: 이전 형식(`question_set`)으로 저장된 접수·판정·릴리스는 새 계약으로 읽히지 않는다. 기존 데이터를 옮기는 코드는 없다(미배포 상태 가정, 확인하지 않음).

## 되돌리는 조건

세트 하나의 실패가 전체를 막는 것이 운영에서 문제가 되면 세트 단위 출고(릴리스 분리)를 계약 변경 요청으로 올린다.
