# ADR-0001: 저장소: 개발·시험은 SQLite, 운영은 PostgreSQL

- 상태: 채택
- 날짜: 2026-10-28 (작성 시점의 코드·문서 기준. 결정 시점은 근거 항목에 적는다)

## 맥락

릴리스 레지스트리(접수, 판정, 승인, 릴리스 매니페스트, 포인터 이력, 영수증)를 어디에 둘지. 최초 구현(2026-10-15, 0b255fc)은 SQLite+파일이었고 PostgreSQL 저장소는 이후 추가했다(cde5fd1, CHANGELOG '(미배포) PostgreSQL 저장소').

## 결정

같은 `Store` 인터페이스와 같은 JSON 텍스트 행 테이블을 SQLite(`SqliteStore`), PostgreSQL(`PostgresStore`), 메모리(`MemoryStore`)가 구현한다. `GATE_DATABASE_URL`이 있으면 PostgreSQL, 없으면 `GATE_DATA_DIR`의 SQLite. 적합성 시험은 세 구현을 같은 코드로 돈다(`tests/test_conformance.py`). 메모리는 이웃 영역이 혼자 시험하는 가짜 구현이다(CLAUDE.md '이 영역이 제공하는 SDK와 메모리 구현').

## 왜 (따른 표준과 근거)

- 개발·시험 기본이 SQLite인 이유: 서버 프로세스 없이 파일 하나로 도는 임베디드 DB라 워크스페이스 공통 규칙(D22: 개발은 컨테이너 밖, 이웃은 메모리 구현으로 혼자 시험)에 맞는다. 읽기 전용 연결(`open_release_reader`)로 게이트 서비스가 멈춰도 포인터를 읽을 수 있다(design.md 6절, WAL).
- 운영이 PostgreSQL인 이유: design.md 6절은 '서비스별 데이터베이스·계정을 가진 서버가 백업·접근 제어·동시 접속의 표준 경로'라고 기록했다. 서버와 수집·판정 잡 여러 프로세스가 같은 레지스트리에 쓰므로 SQLite 파일 하나를 볼륨으로 공유하는 것보다 서버 DB가 표준이다. 결정 번호: 근거 기록 없음(헤드의 D85 2단계에서 영역 저장소를 PostgreSQL로 옮기는 흐름이 있었다는 것까지만 확인, 게이트 전용 결정 문서는 못 찾음).
- 레코드를 JSON 텍스트 한 칼럼으로 둔 이유: 계약 스키마(boundary-contracts)가 레코드 모양을 정하고 이 영역이 쓰기 전에 검증하므로 DB 칼럼이 스키마를 다시 표현할 필요가 없다는 설계 판단(design.md). 외래키·CHECK는 두지 않았다(감사 C10에서 지적됨, 아직 안 고침).

## 검토한 대안과 버리는 이유

- 서버 PostgreSQL만 두기: 개발자가 DB를 띄워야 하고 이웃 영역의 단독 시험이 어려워진다(D22와 충돌). 버림.
- SQLite만 운영에 쓰기: 서버와 잡이 같은 파일을 동시에 쓰는 경합과 백업·접근 제어가 약하다. 이 영역의 쓰기 동시성(advisory lock으로 SQLite의 BEGIN IMMEDIATE를 대체)을 서버 DB가 더 표준적으로 다룬다. 버림.
- 문서 DB·객체 저장소: 근거 기록 없음(검토한 흔적을 못 찾음).

## 결과

두 구현을 같은 시험으로 유지해야 한다(비용). PostgreSQL 시험은 `TEST_DATABASE_URL`이 있을 때만 돈다(없으면 SKIP). 시작 때 스키마를 yoyo 마이그레이션(ADR-0014로 `CREATE TABLE IF NOT EXISTS` 직접 실행을 대체)으로 만들어 런타임 계정에 DDL 권한이 필요하다(감사 C8, 미해결).

## 되돌리는 조건

운영 데이터 규모나 동시성이 SQLite로 충분하다고 측정되고 서버 DB 운영 비용이 문제가 되면 단일 파일로 줄일 수 있다. 측정한 적은 없다('측정 안 함').
