# ADR-0006: 판정 진행은 60초 폴링 Loop, 이벤트가 아니다

- 상태: 채택
- 날짜: 2026-10-28 (작성 시점의 코드·문서 기준. 결정 시점은 근거 항목에 적는다)

## 맥락

접수된 후보를 자동 검사해 승인 대기로 넘기는 일을 언제 돌릴지. 영역이 다른 영역을 깨우지 않는다(D39).

## 결정

서버 안의 `Loop`가 `GATE_POLL_SECONDS`(기본 60)마다 `process_pending`을 한 번 돌린다. 후보 수집(`collect`)은 서버가 아니라 deploy 스케줄러가 부르는 run-once 잡이다. 한 주기에서 일시 오류(UNAVAILABLE)를 만나면 거기서 멈추고 다음 주기로 미룬다.

## 왜 (따른 표준과 근거)

- 근거: D39(영역 사이 자동 연결은 저장소를 보고 일하는 멱등 잡, 직접 호출·이벤트 없음). 이벤트(메시지 큐·웹훅)를 쓰지 않는 이유는 이웃이 우리를 부르는 구조를 만들지 않는다는 D39/D02의 원칙이다. 사람 승인이 마지막이라(ADR-0007) 수 초의 지연이 문제 되지 않는다(브리프 5절 '지연: 요구 없음').
- 60이라는 값의 근거: 근거 기록 없음. 최초 구현(0b255fc)의 기본값이고 측정한 적 없다('측정 안 함').

## 검토한 대안과 버리는 이유

- 이벤트·큐: D39 위반. 버림.
- 더 짧은 주기: 필요를 보인 기록이 없다.

## 결과

장애 중에도 Loop는 죽지 않고 상태가 `/readyz`의 `judging_loop`에 보인다(시험으로 확인). 접수가 많으면 주기가 길어진다.

## 되돌리는 조건

승인 대기 시간이 문제가 되면 주기를 설정으로 줄인다(환경 변수 한 개).
