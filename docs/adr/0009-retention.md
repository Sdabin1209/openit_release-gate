# ADR-0009: 보존·정리 정책

- 상태: 채택 (D88 U4, 잠정 기본값)
- 날짜: 2026-10-28 (작성 시점의 코드·문서 기준. 결정 시점은 근거 항목에 적는다)

## 맥락

접수·판정·릴리스·어댑터 사본이 무한히 늘고 삭제 경로가 없었다(감사 A6/C3).

## 결정

`python -m release_gate prune`(스케줄러가 주기로 부르는 멱등 run-once 잡, `--dry-run` 지원). 반려·미승인 접수와 그 판정 기록은 90일 뒤, 거부·실패 시도 기록은 365일 뒤 삭제한다. 승인·활성 이력(PASS 판정, APPROVE, 릴리스 매니페스트, 포인터 이력, 영수증)은 지우지 않는다. 활성·직전 활성·활성화 전 승인 릴리스(더 새 것)·최근 N(기본 3)개를 뺀 릴리스의 **어댑터 사본**을 지우고 `PRUNED` 표시를 남긴다. 무기한 값(None·0·음수)은 시작을 거부한다. 서버는 스스로 지우지 않는다.

## 왜 (따른 표준과 근거)

- 근거: D88 U4(최소 보존, 무기한 기본값을 없애고 null 거부, 병원 규정이 다르면 설정만 바꾼다). 90일/1년은 D88이 정한 잠정값이고 병원 규정 확정은 OPEN_GAPS. N=3의 근거: 근거 기록 없음(활성+직전 롤백 대상에 여유를 둔 설계 판단).
- 승인 이력을 지우지 않는 이유: 출고 책임의 감사 기록이다(CLAUDE.md '출고는 사람이 정한다').

## 검토한 대안과 버리는 이유

- 서버가 자동 삭제: 의도치 않은 삭제 위험, 스케줄러 일원화(D39). 버림.
- 매니페스트까지 삭제: 감사 기록 손실. 버림.

## 결과

정리된 릴리스로는 롤백·번들 읽기가 FAILED_PRECONDITION(PRUNED)이다. 이 호출을 deploy 스케줄러에 등록하는 일은 deploy의 몫이다(이 영역은 확인하지 못함).

## 되돌리는 조건

병원 규정이 다른 보존 기간을 요구하면 설정만 바꾼다. 어댑터를 오래 보존해야 하면 N을 키운다.
