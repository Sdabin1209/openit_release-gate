# ADR-0003: 번들·어댑터는 파일 시스템에, DB에는 행만, 읽을 때마다 전체 해시 검증

- 상태: 채택
- 날짜: 2026-10-28 (작성 시점의 코드·문서 기준. 결정 시점은 근거 항목에 적는다)

## 맥락

릴리스는 문항 세트 JSON과 어댑터 디렉터리 둘(수 GB 가능)을 묶는다. 서비스(survey-service, 서빙)가 I1·I3 없이 쓰도록 릴리스에 내용을 묶어야 한다(브리프 3-1절).

## 결정

매니페스트·판정 등 레코드는 DB 행, 번들은 `<data>/releases/<release_id>/`에 둔다. 임시 디렉터리(`.tmp-…`)에 만든 뒤 **락 밖**에서 완성하고 트랜잭션 안에서 이름만 바꾼다(`_publish_release_dir`). 어댑터는 같은 파일 시스템에 받아 복사 없이 옮긴다. 읽기·활성화·롤백 검증·번들 전송 때마다 매니페스트 해시, 문항 세트 해시, 어댑터 `directory_hash`, 시스템 프롬프트 해시를 다시 계산한다. 파일 저장소는 **제자리에서** 읽어 해시만 계산하고 복사하지 않는다.

## 왜 (따른 표준과 근거)

- 파일에 두는 이유: 수 GB 바이너리를 DB blob에 넣으면 백업·메모리·트랜잭션 크기 부담이 크다는 일반 관행. 이 영역에서 대안을 측정하거나 비교한 기록은 없다('측정 안 함', 근거 기록 없음). 백업은 'DB 덤프 + releases/ 디렉터리를 한 쌍으로'(runbook).
- 매번 전체 해시를 검증하는 이유: 릴리스 바이트가 환자 경로(서빙)에 들어가므로 변조·손상이 조용히 통과하면 안 된다(D49: 해시는 클라이언트가 재검증하는 규약, 서버도 보내기 전에 검증). 비용: 어댑터 크기에 비례하는 읽기 I/O와 CPU. 이전에는 임시 디렉터리로 통째 복사까지 해서 디스크도 두 배였고, 이번에 복사를 없앴다(해시 계산 자체는 남아 있다). 크기별 소요 시간은 **측정 안 함**.
- 검증 결과를 캐시하지 않은 이유: 파일 mtime·크기 기반 캐시는 같은 크기·시각으로 바꿔치기한 변조를 놓친다. 안전성을 약화하지 않기 위해 매번 계산한다(설계 판단).
- 전송 시 제자리 검증 후 읽기 사이에 파일이 바뀔 수 있는 틈이 있다: 수신 클라이언트가 해시를 다시 확인하므로(D49) 종단 간 무결성은 유지된다.

## 검토한 대안과 버리는 이유

- DB blob(`bytea`/large object): 위 이유로 버림. 단 원자성은 좋아진다(트랜잭션 하나). 되돌릴 조건 참조.
- 객체 저장소(S3 계열): 단일 서버 구성(D40의 가정)에 별도 서비스를 더하는 비용 대비 이득 근거 없음. 버림(검토 기록 없음).
- 해시 캐시: 위 이유로 버림.

## 결과

DB와 파일이 한 쌍이라 백업 시점 불일치 위험이 있다(감사 C7, 문서화 미흡). 커밋 실패 시 행 없는 디렉터리가 남을 수 있으나 읽기는 행 기준이라 보이지 않고 다음 생성 때 치운다. 디스크가 가득 차면 503이고 기록은 남지 않는다. 정리는 `prune`(ADR-0009).

## 되돌리는 조건

어댑터가 수십 GB가 되거나 여러 서버로 나뉘면 객체 저장소와 해시 사이드카(저장 시 계산해 둔 해시를 신뢰하고 주기적으로만 재검증)를 검토한다.
